# Internationalisation (i18n)

**Status:** Phase 1 ships English only per `ROADMAP.md`. This document
exists so the team can add a second locale without re-architecting.

## Why English at launch

The TOR specifies English for the launch realm. The Inception Report
records the open question of whether a second locale is required —
candidates are Liberian Pidgin English (for field-worker UX) and
French (for cross-border partners). Either is achievable on the
scaffolding below; the gating concern is the cost of a competent
translation review by the M&E officer + DPO, not the engineering
work.

Survivor-impact note: GBV terminology is sensitive. Any second-locale
catalog **must** be reviewed by the DPO and a clinician with GBV
casework experience before shipping. A literal machine translation of
intake-form labels can re-traumatise survivors. The DPO sign-off in
the table below is non-negotiable.

## Where catalogs live

```
apps/web/messages/
  en.json           # Web app (next-intl)

apps/mobile/src/i18n/
  index.ts          # t() helper + locale state
  en.json           # Mobile app
```

The two apps keep separate catalogs deliberately. They serve different
audiences (admin staff vs. field workers) and use different UI
vocabularies; merging them would produce strings that fit neither.

Shared concepts that should agree across surfaces (role names,
violence types, indicator names) live in the JSON files in both apps
under the same key paths (`roles.*`, `case.violenceTypes.*`, etc.).
A linter check verifying they stay in sync is a follow-up.

## Web app — next-intl

`apps/web/src/i18n/config.ts` lists supported locales.
`apps/web/src/i18n/request.ts` is the next-intl `getRequestConfig`.
`apps/web/next.config.ts` registers the next-intl plugin.
`apps/web/src/app/layout.tsx` wraps the tree in
`NextIntlClientProvider`.

Usage in a server or client component:

```tsx
import { useTranslations } from 'next-intl';

export default function MyComponent() {
  const t = useTranslations('cases.list');
  return <h1>{t('title')}</h1>;
}
```

ICU placeholders work as expected:

```tsx
t('greeting', { name: user.displayName })
```

For server-side metadata (page titles, descriptions), use
`getTranslations()` from `next-intl/server`.

## Mobile app — lightweight `t()`

`apps/mobile/src/i18n/index.ts` is a small synchronous helper. It
mirrors the next-intl call shape (`t('key.path', { var: 'value' })`)
so call sites are portable.

```tsx
import { t } from '../i18n';

<Text>{t('case.newCase')}</Text>
<Text>{t('case.step', { current: 2, total: 3 })}</Text>
```

It supports ICU plural form for counts:

```tsx
t('sync.pending', { count: 3 })
// => "3 pending records"
```

The helper is sync — no async catalog loading. The whole `en.json`
ships in the bundle. That's appropriate for the catalog size we
expect (a few hundred strings); switching to lazy loading is a
future refactor if the catalog grows beyond a few hundred KB.

## Adding a second locale

1. **Confirm the requirement.** A new locale is a meaningful product
   change, not a code change. The Inception Report or a change order
   from MOGCSP is the trigger.
2. **Get translations.** A qualified human translator with
   gender-based-violence vocabulary expertise is required. A list
   of approved translation providers lives in the MOGCSP document
   system.
3. **Web**:
   - Drop `apps/web/messages/<locale>.json` next to `en.json`
   - Add the locale code to `LOCALES` in `apps/web/src/i18n/config.ts`
   - Decide locale source: cookie + `accept-language` header is the
     usual default. Update `apps/web/src/i18n/request.ts` accordingly
   - Add a `LocaleSwitcher` component to the dashboard top bar
   - For routed locales (`/en/...`, `/fr/...`), refactor to next-intl's
     App Router routing model. Until then, the locale is global per
     session.
4. **Mobile**:
   - Drop `apps/mobile/src/i18n/<locale>.json` next to `en.json`
   - Add the locale code to `LOCALES` in `apps/mobile/src/i18n/index.ts`
     and import the JSON in `CATALOGS`
   - Source the locale from `expo-localization` device settings, with
     a per-user override stored in `expo-secure-store`. Persist the
     override across app launches
   - Re-render the UI on locale change — the current synchronous
     helper does not auto-trigger React updates, so wrap it in a
     React context that re-renders subscribers
5. **Translation review**:
   - DPO sign-off on every survivor-facing string (intake form labels,
     incident-detail prompts, error messages)
   - M&E officer sign-off on indicator and report labels
   - QA pass on a real device with the new locale active
6. **Update this document** with the new locale's name and review date.

## Conventions

- **Key naming**: dotted, namespace.section.label. Example:
  `cases.list.title`, `case.violenceTypes.PHYSICAL`.
- **Reuse `common.*`** for genuinely shared strings (loading, retry,
  cancel). Avoid copying them into multiple namespaces.
- **One string per concept.** If two screens say "Save", use
  `common.save` in both — don't invent `cases.save` and
  `beneficiaries.save`.
- **Plurals**: use the ICU plural form (`{count, plural, =0 {none}
  =1 {one} other {# many}}`). Never concatenate.
- **No HTML in catalog values.** If you need a styled span, use the
  next-intl rich-text feature or split the string and let the
  component compose it.
- **Don't put PII in a catalog.** Catalog values must never mention a
  real survivor's name, county, or case ID. They're shared assets.

## Stage 4 verification

Before pen-test, the `i18n` deliverable is checked:

- [ ] Every user-facing string in the web app's primary screens is in
      `en.json` (no hard-coded strings)
- [ ] Every user-facing string in the mobile case-intake screen is in
      `en.json`
- [ ] `t('missing.key')` falls back to the key (visible miss, no
      blank UI)
- [ ] Adding a second locale would not require touching any
      component (ratchet check)

These items live as rows in `docs/pen-test/hardening-checklist.md`
once the second-locale decision is taken.
